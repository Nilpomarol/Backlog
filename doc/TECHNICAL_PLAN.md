# Shared App Backlog — Technical Plan

## 1. Goal

Build a small private backlog web application for personal applications, family, and close friends.

The implementation must:

- work well on phones and desktop browsers;
- remain available after long periods without activity;
- have no required monthly infrastructure cost for the expected usage;
- enforce ownership, visibility, voting, and administrator permissions on the server;
- remain simple to develop, deploy, test, and maintain.

The system is not intended to become a generalized project-management platform.

## 2. Selected Architecture

Use a responsive React single-page application, a small serverless API, and a Turso relational database.

```text
Browser
  ├── React application
  └── Firebase Authentication
          │
          ▼
Cloudflare Worker
  ├── verifies Firebase identity
  ├── checks invitation and permissions
  ├── exposes the application API
  └── serves the compiled frontend
          │
          ▼
Turso database
```

The browser must never connect to Turso using the application's database token. All database access passes through the API.

Using one Cloudflare deployment for the frontend and API keeps them on the same origin, avoids CORS configuration, and simplifies authentication and deployment.

## 3. Technology Stack

### Frontend

- React
- TypeScript
- Vite
- React Router
- TanStack Query
- Tailwind CSS
- selected shadcn/ui or Radix primitives where they save implementation time
- React Hook Form
- Zod
- Lucide icons

Do not introduce Redux, Zustand, or another global state library initially. TanStack Query owns server state; React context is sufficient for authentication and small UI-only state.

### API

- Cloudflare Workers
- Hono
- TypeScript
- Zod request and response validation
- Drizzle ORM

The API contains authorization and application rules. Route handlers should call small domain-oriented functions, but the project should avoid excessive repository, service, or dependency-injection layers.

### Database

- Turso Cloud
- SQLite-compatible schema
- `@libsql/client` for the established Drizzle integration
- Drizzle Kit for schema generation and migrations

Turso is selected because its free tier does not pause inactive databases or require a manual resume operation. Its expected limits are substantially larger than this application needs.

### Authentication

- Firebase Authentication
- Google sign-in for the first version
- invited-email allowlist stored in Turso

Firebase identifies the user. The API, not Firebase alone, determines whether that user can access application data and what role they have.

### Testing

- Vitest for unit tests
- React Testing Library for important component behavior
- local SQLite or libSQL database for API integration tests
- Playwright for end-to-end desktop and mobile flows

### Deployment

- Cloudflare Workers and Static Assets
- Turso Cloud
- Firebase Authentication
- GitHub for source control, pull-request validation, and Cloudflare build triggers

The repository deploys directly with Wrangler using `wrangler.jsonc`. Cloudflare
Workers Builds runs `npm run build` and `npx wrangler deploy` after changes are
merged to `main`. Public Firebase web settings are supplied as build variables;
Turso credentials and the Firebase project ID are managed as Worker runtime
variables and secrets.

Use the current stable releases when the project is initialized and commit the package lockfile. Pin an active Node.js LTS version in the repository.

## 4. Authentication and Invitations

### Sign-in flow

1. The user signs in with Google through Firebase Authentication.
2. The frontend sends the Firebase ID token with API requests.
3. API middleware verifies the token signature, issuer, audience, expiry, and verified-email claim.
4. The API normalizes the email address to lowercase.
5. Access is granted only if a matching invited user exists in the `users` table.
6. On the first successful login, the API links the Firebase user ID to the invited user record.

An authenticated Firebase account that is not present in the allowlist receives an `Access denied` screen and cannot read or modify application data.

### User records

Invited users are managed through an administrator interface, with scripts kept
as an operational fallback. Revoking access disables future API sessions while
preserving the user record and all authored cards.

The `users.role` field is controlled only through migrations or administrator tooling. It must never be accepted from a browser request.

### Roles

- `admin`
- `user`

Card ownership is determined by `backlog_items.creator_id`; it is not a separate global role.

## 5. Database Schema

Use text identifiers generated by the application, UTC timestamps, foreign keys, check constraints, and explicit indexes.

### `apps`

- `id` — text primary key
- `name` — text, required
- `icon` — text, required
- `description` — text, optional
- `sort_order` — integer, required
- `is_active` — integer boolean, required, default true
- `created_at` — integer timestamp, required

Applications can be created, edited, archived, and restored through the
administrator interface. Archiving is used instead of destructive deletion so
existing cards remain intact.

### `users`

- `id` — text primary key
- `firebase_uid` — text, optional until first login, unique
- `email` — normalized text, required, unique
- `name` — text, required
- `role` — `admin` or `user`
- `created_at` — integer timestamp, required
- `updated_at` — integer timestamp, required

This table serves as both the invitation allowlist and the application profile table.

### `backlog_items`

- `id` — text primary key
- `app_id` — foreign key to `apps.id`
- `creator_id` — foreign key to `users.id`
- `title` — text, required
- `description` — text, optional
- `type` — `bug`, `feature`, `improvement`, or `task`
- `status` — `backlog`, `in_progress`, `in_review`, `done`, or `discarded`
- `visibility` — `shared` or `internal`
- `created_at` — integer timestamp, required
- `updated_at` — integer timestamp, required

New user-created cards always start as `shared` and `backlog`. Only an administrator can create or change an internal card or change status.

### `votes`

- `item_id` — foreign key to `backlog_items.id`
- `user_id` — foreign key to `users.id`
- `created_at` — integer timestamp, required
- composite primary key on `item_id + user_id`

The composite primary key guarantees one vote per user and card. Users cannot vote for their own cards or for internal cards.

### `subtasks`

- `id` — text primary key
- `item_id` — foreign key to `backlog_items.id`
- `title` — text, required
- `completed` — integer boolean, required, default false
- `position` — integer, required
- `created_at` — integer timestamp, required
- `updated_at` — integer timestamp, required

Subtasks are deleted when their parent card is deleted.

### Indexes

Create at least:

- `backlog_items(app_id, status)`
- `backlog_items(app_id, visibility)`
- `backlog_items(creator_id)`
- `votes(item_id)`
- `votes(user_id)`
- `subtasks(item_id, position)`

Use `EXPLAIN QUERY PLAN` when changing backlog queries to confirm that filters use indexes.

## 6. Permission Matrix

Permissions are enforced in the API on every request. Hiding a control in the frontend is never considered authorization.

| Operation | Administrator | Card owner | Other user |
|---|---:|---:|---:|
| Read shared card | Yes | Yes | Yes |
| Read internal card | Yes | No | No |
| Create shared card | Yes | Yes | Yes |
| Create internal card | Yes | No | No |
| Edit card content | Yes | Own card | No |
| Delete card | Yes | Own card | No |
| Change status | Yes | No | No |
| Change visibility | Yes | No | No |
| Manage subtasks | Yes | Own card | No |
| Vote on shared card | Yes | Other cards | Other cards |

For owner edits, the API accepts only `appId`, `title`, `description`, and `type`. It ignores no unexpected fields: unknown or protected fields cause validation failure.

Administrator status and visibility changes use dedicated endpoints so their authorization is explicit and easy to test.

## 7. API Contract

All routes are under `/api`. Except for a health endpoint, every route requires a verified and invited user.

### Session

- `GET /api/me` — return the current application user and role

### Applications

- `GET /api/apps` — list active applications and active-card counts

Application creation, editing, archiving, and restoration are administrator-only API operations.

### Cards

- `GET /api/apps/:appId/items` — list permitted card summaries and apply filters
- `GET /api/items/:itemId` — return permitted card details
- `POST /api/items` — create a card
- `PATCH /api/items/:itemId` — edit allowed card content
- `DELETE /api/items/:itemId` — delete a permitted card
- `PATCH /api/items/:itemId/status` — administrator-only status change
- `PATCH /api/items/:itemId/visibility` — administrator-only visibility change
- `GET /api/apps/:appId/items/similar?title=...` — return possible duplicates

### Votes

- `PUT /api/items/:itemId/vote` — add the current user's vote idempotently
- `DELETE /api/items/:itemId/vote` — remove the current user's vote

### Subtasks

- `POST /api/items/:itemId/subtasks` — create a subtask
- `PATCH /api/subtasks/:subtaskId` — edit title or completed state
- `DELETE /api/subtasks/:subtaskId` — delete a subtask
- `PUT /api/items/:itemId/subtasks/order` — reorder all subtasks transactionally

Use consistent JSON error responses with a stable error code, a safe user-facing message, and the appropriate HTTP status.

## 8. Queries and Data Rules

### Card summaries

The backlog query returns only information required by card summaries:

- title;
- type;
- creator name and administrator-created indicator;
- vote count and whether the current user voted;
- completed and total subtask counts;
- internal indicator when the viewer is an administrator.

The full description is fetched only for card details.

### Active-card count

An active card has one of these statuses:

- `backlog`
- `in_progress`
- `in_review`

`done` and `discarded` cards are not included in application active-card counts.

### Duplicate suggestions

After at least three title characters, debounce requests by approximately 250 milliseconds.

The API:

1. loads visible, non-discarded cards from the same application;
2. normalizes case and punctuation;
3. ranks candidates using a small string-similarity function;
4. returns only the closest few matches.

No AI, embeddings, or external search service is needed.

## 9. Frontend Routes

- `/` — role-aware overview (triage summary for administrators, "your requests" for members)
- `/a/:appId` — application backlog (board and list views)
- `/a/:appId/new` — create a request
- `/r/:itemId` — request detail, with inline editing
- `/inbox` — cross-application triage (administrators)
- `/mine` — requests you reported and voted for
- `/settings/profile`, `/settings/people`, `/settings/apps`

Sign-in and access-denied are rendered in place by the application shell rather than as separate
routes, so a deep link survives authentication instead of being lost to a redirect.

Filters, sorting, the view toggle and the discarded toggle all use URL search parameters, so every
view is linkable and survives a refresh.

## 10. Responsive Interface

Design mobile-first and progressively enhance the backlog for wider screens.

### Desktop

- Show Backlog, In Progress, In Review, and Done as simultaneous columns.
- Keep filters above the board.
- Use dedicated routed card details, with an optional wide side-panel presentation later.
- Show administrator status controls without relying on drag-and-drop.

### Mobile

- Show every status as a single scrolling list with sticky, collapsible group headers. The
  member's core question — "did my request move?" — spans statuses, so tabs would hide most of
  the board behind an extra tap. Revisit tabs if one application exceeds roughly 60 open requests.
- Use full-width cards and full-page card details and forms.
- Keep the application header and status tabs visible while scrolling where practical.
- Place the create action within easy thumb reach.
- Use touch targets of at least 44 by 44 CSS pixels.

Do not require hover, precise pointer input, or drag-and-drop. A status selector is the version-one workflow control on all devices.

### Accessibility

- Use semantic controls and headings.
- Ensure complete keyboard navigation.
- Provide visible focus states.
- Associate validation messages with their inputs.
- Do not communicate type, status, visibility, or authorship using color alone.
- Respect reduced-motion preferences.

## 11. Client Data Management

TanStack Query owns all API data.

Suggested query-key groups:

- `['me']`
- `['apps']`
- `['items', appId, filters]`
- `['item', itemId]`
- `['similar-items', appId, normalizedTitle]`

Use optimistic updates only for low-risk, easily reversible actions such as voting and subtask completion. Card deletion, status changes, visibility changes, and reordering should wait for a successful API response.

## 12. Security Requirements

- Keep `TURSO_AUTH_TOKEN` only in Cloudflare secrets.
- Never place private credentials in `VITE_` environment variables.
- Verify Firebase tokens on every authenticated API request.
- Check token audience, issuer, expiry, signature, and verified email.
- Reject users who are not in the Turso allowlist.
- Validate all path parameters, query parameters, and bodies with Zod.
- Use parameterized database queries through Drizzle.
- Return no internal card information in errors, counts, duplicate suggestions, or list endpoints for non-administrators.
- Add request-size limits and conservative rate limits to write endpoints.
- Log request IDs and safe error metadata, but never authentication tokens or sensitive descriptions.

## 13. Environment Configuration

### Public frontend configuration

- Firebase API key
- Firebase auth domain
- Firebase project ID

Firebase's browser configuration identifies the Firebase project and is not treated as a private server credential.

### Cloudflare secrets

- `TURSO_DATABASE_URL`
- `TURSO_AUTH_TOKEN`
- Firebase project or audience identifier needed for token verification

Provide `.env.example` and local Wrangler variable examples without real secrets.

## 14. Testing Strategy

The highest-risk behavior is authorization, so permission tests take priority over broad component-test coverage.

### API integration tests

Cover every role in the permission matrix, including:

- unknown Firebase user rejected;
- ordinary user cannot read internal cards;
- owner can edit allowed fields on their card;
- owner cannot change status, visibility, creator, or timestamps;
- administrator can manage any card;
- user cannot edit another user's card;
- duplicate vote is harmless and does not create a second row;
- self-voting and voting on internal cards are rejected;
- only owner or administrator can manage subtasks;
- subtask ordering is validated and updated atomically.

### Frontend tests

Test validation, permission-dependent controls, filters, and important empty and error states.

### End-to-end tests

Run critical flows in at least:

- desktop Chromium;
- a narrow touch viewport comparable to a modern phone;
- WebKit for the principal mobile flow.

Critical flows are login, card creation, owner editing, administrator status change, voting, duplicate suggestion, and subtask management.

## 15. Backup and Recovery

Turso Free currently provides a short point-in-time recovery window, so platform recovery alone is not sufficient.

- Keep every schema migration and seed definition in source control.
- Create a regular logical database export.
- Store exports in private, encrypted storage outside Turso.
- Keep multiple dated exports and periodically test restoration into a temporary database.
- Never commit production data or credentials to the repository.

A weekly export is sufficient initially because the application is small and low-traffic. Increase the frequency if usage becomes regular or the cost of losing a week of changes becomes unacceptable.

## 16. Implementation Order

### Phase 1 — Foundation

- initialize React, Vite, TypeScript, Tailwind, and Cloudflare tooling;
- create the Hono API and same-origin local development setup;
- configure Firebase Authentication;
- configure Turso, Drizzle schema, migrations, and local test database;
- add invited administrator and ordinary test users;
- implement authentication middleware and `/api/me`;
- add automated authorization-test helpers.

Exit condition: invited users can sign in, uninvited users are rejected, and the API can securely identify roles.

### Phase 2 — Complete backlog slice

- applications screen and active-card counts;
- responsive backlog queries and card summaries;
- card details;
- card creation, editing, and deletion;
- administrator status and visibility controls;
- shared, internal, and administrator-created indicators.

Exit condition: the application is useful for managing cards before collaboration extras are added.

### Phase 3 — Collaboration

- voting and vote removal;
- duplicate-title suggestions;
- subtask creation, editing, completion, deletion, and ordering;
- card-level subtask progress.

Exit condition: all core behavior in the product specification is implemented.

### Phase 4 — Responsive polish

- desktop columns and mobile status tabs;
- minimum filters and discarded view;
- loading skeletons and empty states;
- validation, error, confirmation, and retry behavior;
- accessibility review.

### Phase 5 — Release

- run the complete authorization suite;
- run Playwright desktop and mobile flows;
- configure production secrets and Firebase domains;
- deploy a preview and validate with administrator and ordinary accounts;
- configure database exports;
- deploy production.

## 17. Explicit Non-Goals

Do not add in version one:

- native Android or iOS applications;
- offline editing or local-first synchronization;
- drag-and-drop workflow controls;
- real-time subscriptions;
- comments, notifications, attachments, or activity history;
- semantic or AI-powered duplicate detection;
- complex state management;
- microservices or a generalized workflow engine.

The responsive web application is the phone and desktop product.

## 18. Technical Principle

Choose the smallest implementation that securely satisfies the specification.

Turso stores the relational data, Firebase proves identity, and the Hono API owns every authorization and business rule. This boundary must remain explicit throughout implementation.
